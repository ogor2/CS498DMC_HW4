Q1: FoundationDB separates its architecture into TMS and the SS so they can independently scale. If there are more reads, more storage servers can be added to the storage system. If more writes, we can scale by increasing capacity in proxies, resolvers, and log servers.
Q2: During the write transaction in FDB, the component that is responsible for detecting read-write conflicts between concurrent transactions is the resolver. During the commit process, after the sequencer assigns a commit version, the resolver checks to see if another committed transaction modified any key in the transaction read range. If a conflict is found, then the transaction is aborted. 
Q3: FDB's sequencer assigns both a read version and a commit version to each transaction as it helps determine at which point of time the database was read. It relates to consistency guarantees as we can ensure the reads see a consistent version of the database. Also, it helps with ordering the commits which provides strict serializability.
Q4: Snapshot reads differ from regular reads as they do not add to the read conflict ranges. Snapshot prevents the transaction from being aborted due to concurrent writes. A situation where snapshot reads are better than read conflict ranges is for analytical tasks or background tasks where the read values do not affect the transactions write values.
Q5: What makes FDB claim it has cheap recovery is because its transaction system is separate from the storage systems. When the system is running the log servers store committed changes while the storage servers pull them and store them asynchronously. When a failure occurs, FDB determines the recovery version from the log servers. The existing logs or copied or preserved which helps it recover faster and cheaper.
